# DustwireMP v0.3 — RDR1 build profile

The launcher records a stronger executable fingerprint for the target RDR.exe:

- PE machine
- PE timestamp
- SizeOfImage
- file size
- .text RVA
- .text virtual size
- .text FNV-1a 64 hash
- Windows file version
- SHA-256 of the complete executable file

By default, the launcher remains permissive for build discovery. It requires x64 but does not require an exact profile.

## Historical build already observed

The previous FrontierMP repository contains a local probe result for:

D:/Red Dead Redemption/RDR.exe

with:

~~~text
file_version=1.0.42.46611
pe_timestamp=0x673783F3
image_size=0x5A5EC600
text_rva=0x1000
text_size=0x104A140
text_fnv1a64=0xB213CBF3DEE9B6BF
machine=AMD64
~~~

This is evidence from the earlier development repository, not proof that the current installation has remained unchanged. The current executable must still be checked locally. The launcher does not require RDR.exe to be next to its own binaries.

## Capture the current profile

From the DustwireMP repository:

~~~bat
build.bat
run_build_probe.bat "D:\Red Dead Redemption\RDR.exe"
~~~

The probe only reads the executable file. It does not launch RDR.exe and does not inject the client module.

Copy the observed values into config/launcher.ini when a strict profile is ready.

A strict profile can use the PE/text fingerprint and/or SHA-256. The SHA-256 is strongest for identifying the exact file; the section fingerprint makes the build registry easier to compare with the previous reverse-engineering work.

## Launcher log location

When launched through run_launcher.bat from the repository root, the current launcher writes:

~~~text
logs/launcher.log
~~~

When the executable is started outside the repository layout, it falls back to a logs directory next to the launcher executable.

The launcher log contains the complete observed fingerprint:

~~~text
PE machine=0x... x64=1 timestamp=0x... image_size=0x... file_size=... text_rva=0x... text_size=0x... text_fnv1a64=0x... file_version=... sha256=...
~~~

## Game-thread finding from the previous repository

The earlier FrontierMP implementation did not use its arbitrary worker thread as the game-facing execution context.

It implemented a GameThreadDispatcher that hooks the native scrThread::Wait handler and pumps a bounded task queue from that context. It also tracked GET_THIS_SCRIPT_ID and GET_SCRIPT_NAME so that only known script contexts could authorize the dispatcher.

For DustwireMP, this is useful as a reference for a future Rdr1GameThreadSource or game-thread dispatcher. It should not be called a verified engine frame tick yet.

The previous implementation also kept build detection separate from runtime compatibility: a known executable fingerprint enabled pattern scanning, while individual game symbols still required their own validation.

## Relationship to the game tick

A build fingerprint identifies the executable. It does not prove that a particular hook or native is correct.

The next implementation stage is:

~~~text
exact RDR.exe fingerprint
    ->
verified game-thread entry
    ->
Rdr1GameThreadSource
    ->
safe GameBridge access
    ->
local actor
~~~

Do not add an RDR1 address solely because it exists in the historical source. Verify the candidate against the exact executable being supported.
